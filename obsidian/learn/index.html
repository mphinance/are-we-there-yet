This is a field guide to getting more out of large language models, written to be read with no connection: on a plane, in a fjord, on a ship somewhere north of the Faroe Ridge.

It assumes you already use these tools daily and are past the "write me a haiku" phase. The goal is not tricks. The goal is a mental model accurate enough that you can predict what the model will do before you hit enter, and debug it when you are wrong.

Everything factual here is current as of August 2026. Model names, prices, and parameters move fast, so treat section 11 as perishable and sections 1 through 10 as durable.

The one idea

Almost every failure you will hit is a context failure, not an intelligence failure. The model did not know something you assumed it knew, or it knew too many things and the important one got diluted. Debug context first. Debug phrasing last.

Section 1How the thing actually works

In one line

It is a next-token predictor with no memory, reading a flat buffer of text you rebuild from scratch on every single turn.

Tokens, not words

Text is chopped into tokens: roughly 3 to 4 characters of English, less for code, much less for non-Latin scripts. Everything is priced, budgeted, and limited in tokens. A useful habit is to stop estimating in words entirely.

Do not use an OpenAI tokenizer to count tokens for Claude. tiktoken undercounts Claude tokens by roughly 15 to 20 percent on prose and much more on code. Use the provider's own count endpoint if the number matters.

The model is stateless

This is the fact people most often fail to internalize, and it explains an enormous amount of otherwise confusing behavior.

There is no conversation living on a server somewhere. Every time you send a message, the client resends the entire conversation: system prompt, tool definitions, every previous turn, every tool result, and your new message. The model reads all of it fresh and predicts what comes next. Then it forgets everything.

Consequences that follow directly, and that are worth reasoning through until they feel obvious:

  • A long conversation costs more per turn than a short one, because you are resending more each time. Cost grows quadratically over a session, not linearly.
  • "Remember what I said earlier" is not a memory operation. The earlier text is right there in the buffer. If the model missed it, that is an attention or dilution problem, not amnesia.
  • Starting a fresh session genuinely resets everything. There is no residue, no learning, no accumulated understanding of you unless something wrote it to a file.
  • Anything you want the model to "know" next week has to live somewhere on disk that gets read back in. That is the entire premise behind project instruction files, memory tools, and notes directories.

The context window

The window is the maximum size of that flat buffer. Current frontier Claude models hold 1 million tokens; the smaller fast models hold 200,000. That sounds infinite and is not, for two reasons.

First, agentic work fills it startlingly fast. A single file read can be 20,000 tokens. A verbose test run can be 30,000. Twenty tool calls into a debugging session you can be at 300,000 without having done anything unusual.

Second, and more important: attention is not uniform across the window. Material at the very beginning and the very end of the buffer gets weighted more heavily than material in the middle. This is a real, measured effect and it is why a critical instruction buried at token 400,000 of a long session behaves as though you never said it. The fix is placement, not emphasis.

Practical

If something must not be missed, it goes in the system prompt (start of buffer) or in the most recent turn (end of buffer). Shouting at it in the middle does not work. This is also why re-stating a key constraint in your latest message often "fixes" a model that seemed to be ignoring you: you moved the instruction to a high-attention position.

Thinking, effort, and what they actually buy

Modern Claude models can generate reasoning tokens before their visible answer. On the current generation this is adaptive: the model decides per request how much to think, rather than you handing it a fixed token budget. The old fixed-budget parameter is gone and returns an error on current models.

What you control instead is effort, a five-step dial: low, medium, high, xhigh, max. The default is high. Effort governs more than reasoning depth; it also governs how many tool calls the model makes, how much it explores before committing, and how much preamble it writes.

Two things surprise people:

  • Effort is not a quality slider you should max out. Higher effort on a simple task produces overthinking, unrequested refactors, and worse results, not better ones. Low and medium on a current frontier model routinely beat the top setting of the previous generation.
  • Higher effort can be cheaper end to end. On agentic work, more thinking up front often means fewer wrong turns, fewer tool calls, and fewer rounds. Per-request cost goes up; total task cost goes down. Measure the task, not the request.

You never see the raw chain of thought. On current models you get either nothing or a readable summary, depending on a display setting. The reasoning genuinely happened and was genuinely billed either way.

Why it makes things up

Hallucination is not a bug bolted onto an otherwise truthful system. The model produces a plausible continuation. When the true continuation is in its weights, plausible and true coincide. When it is not, you get plausible alone, delivered with exactly the same fluency.

This predicts precisely where you should distrust output:

  • Specific and rare beats specific and common. Version numbers, exact API signatures for niche libraries, page numbers, case citations, obscure config keys. The shape is memorable; the content is not.
  • Anything after the training cutoff. The model does not know what it does not know about recent events, and will confidently interpolate.
  • Anything you led it to. "What was the name of that flag again?" presupposes a flag exists. The model will supply one.

The structural fix is not "tell it not to hallucinate," which does close to nothing. It is to change the task from recall to reading: give it the document, the file, the search result. A model summarizing text in front of it is far more reliable than a model recalling text from memory.

Section 2Prompting that survives contact

In one line

Give it what only you know, say what you actually want at a normal volume, and stop writing incantations.

The hierarchy of levers

Ranked by how much they actually move outcomes, largest first:

  1. Context. Who this is for, what it plugs into, what the constraints are, what "good" looks like here. This is the whole game.
  2. Task specification. The actual deliverable, its scope, its boundaries.
  3. Examples. Two or three, deliberately varied.
  4. Effort and model choice. A parameter, not a sentence.
  5. Phrasing. Nearly irrelevant on modern models, and the thing people spend the most time on.

If you find yourself rewording a sentence for the fourth time, stop. You are optimizing lever five. Go back and ask what the model does not know that you do.

Give it the reason, not just the request

Compare:

Thin

"Write a summary of this report."

Loaded

"I need to brief our CFO on this vendor report before a renewal call Thursday. She has not read it and will not. She cares about cost exposure and contract lock-in, not implementation detail. Write what she needs."

The second version is not longer for the sake of being longer. Every clause changes an actual decision the model has to make: audience, depth, framing, what to cut. Without them the model picks defaults, and defaults are generic because generic is the safest guess about an unknown reader.

The general form: I am doing X for Y, who needs it in order to Z. With that in mind, do the following.

Say it once, at normal volume

Older, less steerable models genuinely needed shouting. Current models follow the system prompt closely, which means old emphasis now overshoots.

Written for an older modelWhat to write now
CRITICAL: You MUST use this tool when...Use this tool when...
If in doubt, use the search toolDelete it. It causes constant unnecessary searching.
Be thorough. Do not be lazy. Do not stop early.Delete it. Current models are proactive by default.
Think step by stepDelete it. Reasoning is a parameter now, not an incantation.
Try to include a summary if possibleInclude a summary. Hedges get read literally as permission to skip.

There is a second-order effect worth knowing: when five instructions are all marked critical, the marker stops carrying information. And the register of your prompt becomes the register of the output. An anxious, hedge-laden, all-caps prompt produces cautious, hedging, over-qualified answers.

Describe success, do not enumerate failure

Long prohibition lists work worse than they look like they should. Two reasons: describing a failure mode in detail can anchor the model toward it, and a wall of "never do X" leaves the model with no positive target, so it optimizes for not-being-wrong rather than for being useful.

Prohibition stack

"Do not be verbose. Do not use bullet points. Do not add caveats. Do not start with 'Certainly'. Never use headers."

Positive target

"Answer in prose, at the length the question actually needs. Lead with the answer."

Keep prohibitions where they encode a real constraint: a refund cap, a compliance rule, a thing the business must not promise. Those are context, and context is never clutter. Drop the ones that just describe an output style you dislike, and state the style you want instead.

Examples are the strongest signal in the prompt

Stronger than your instructions. If your instruction says "be concise" and your single example is four paragraphs, you get four paragraphs. The example wins.

This cuts both ways, and the failure mode has a name: gold-example anchoring. One perfect example freezes its length, tone, structure, and even its idiosyncrasies into every output. Use two or three deliberately different examples so the model infers the principle rather than copying the artifact. Label them as illustrative.

State the boundary

Current frontier models are autonomous by default, which is usually what you want and occasionally not. The failure looks like: you asked a question and got a refactor. You described a problem and got a fix applied. You asked for an assessment and got a pull request.

The fix is one sentence in the system prompt, and it is remarkably effective:

"Deliver what was asked, at the scope intended. Make routine judgment calls yourself; check in only when different readings would lead to materially different work. When someone is describing a problem or thinking out loud rather than requesting a change, the deliverable is your assessment: report and stop. If you think the ask is wrong, say so in a sentence and proceed as asked anyway."

Stop telling it to check its work

This one inverts a piece of advice that used to be correct, which makes it easy to miss.

"Double-check your answer" and "add a final verification step" were good instructions two model generations ago. On the current frontier they cause over-verification: redundant passes, re-derivation of things already established, extra subagents spawned to check work that was already checked. The models verify by default now. Deleting the instruction reduces the waste with no measurable loss in correctness.

Same category, same direction: forced progress-update choreography ("summarize after every three tool calls") is now redundant scaffolding. The models narrate on their own, and often too much rather than too little.

The general rule

Prompts are per-model artifacts. A line that is load-bearing on one generation is dead weight on the next, and actively harmful on the one after. Every model release is a reason to re-read your prompts and delete, not just add. Nobody owns that deletion, which is why prompts accumulate the union of every generation's workarounds.

A structure that holds up

Not a magic template. Just an ordering that puts stable material first, which matters for caching (section 4) and for attention (section 1).

1. Role and situation      one or two sentences, no more
2. Context                 audience, product, environment, constraints
3. The task                what to produce, at what scope
4. Quality bar             what good looks like here, specifically
5. Boundaries              what not to touch, when to stop and ask
6. Examples                two or three, varied, labeled illustrative
7. The specific request     <-- the only volatile part

Items 1 through 6 should be byte-identical across requests. Item 7 changes. Keeping that split clean is worth real money, which is section 4.

Section 3Context engineering

In one line

Curating what goes into the window is now a bigger skill than writing what goes into the prompt.

The budget framing

Treat the window as a budget with three competing claims on it: the instructions that shape behavior, the material the task actually needs, and the accumulated debris of the session so far. The third one grows without asking permission and crowds out the first two.

Signs your context has gone bad, in rough order of how early they appear:

  • The model re-reads a file it already read.
  • It re-derives a conclusion you reached together twenty turns ago.
  • It contradicts a constraint you set early in the session.
  • It starts hedging on things it was confident about.
  • It suggests starting a new session.

The first one is the tell. When you see it, the useful move is almost always to start fresh with a tight, deliberate summary rather than to keep pushing.

Poisoning

A specific and underappreciated failure: once a wrong fact enters the context, it stays. The model treats its own earlier output as established. If it misread a config file on turn three, that misreading is load-bearing on turn thirty, and every conclusion built on it inherits the error.

You cannot fix this by arguing. Correcting it in a later turn leaves both the wrong version and the correction in the buffer, and the model now has to reconcile them, which sometimes works and sometimes produces a muddle. For a genuinely poisoned session, restart and carry forward only what you know is true.

The three mechanisms for keeping it lean

MechanismWhat it doesUse when
Context editingDeletes stale tool results and old reasoning blocks outrightLong tool-heavy runs where old outputs are genuinely dead
CompactionSummarizes earlier turns into a compact block, server sideLong conversations approaching the window limit
Memory (files)Writes to disk, survives the session endingAnything that should still be true next week

These are complementary, not alternatives. Editing prunes, compaction summarizes, memory persists. Long-running agents typically use all three.

One implementation trap on compaction: the summary comes back as a block in the response, and you have to pass it back on the next request. Code that extracts only the text string and appends that will silently drop the compaction state and quietly stop working.

The memory file pattern

Worth knowing even outside a formal memory tool, because it is the mechanism behind every "the AI remembers my project" feature you have used.

Give the model a directory it can read and write. Tell it to check there before starting and to record what it learns. Then give it a format, because without one you get an unusable pile:

"One lesson per file, with a one-line summary at the top. Record corrections and confirmed approaches alike, and say why each mattered. Do not save what the repository or the chat history already records. Update an existing note rather than creating a near-duplicate. Delete notes that turn out to be wrong."

The last two clauses are the ones people leave out, and they are why memory directories rot into contradictory sludge after a month.

Never

Do not put credentials in memory files, system prompts, or conversation history. All three are durably persisted and replayed into every future session that touches them. A key written once is a key leaked repeatedly.

Retrieval beats recall, always

Whenever you can convert "what do you know about X" into "here is X, work with it," do it. Every measure of reliability improves: fewer fabrications, better citations, more calibrated uncertainty. This is the entire reason search tools, file reading, and document upload exist, and it is why an agent with tools beats a bigger model without them on most real tasks.

Section 4Caching, and where the money goes

In one line

Caching is a prefix match, so one timestamp at the top of your prompt can cost you the entire discount.

The single invariant

Prompt caching works on an exact byte-prefix match. The cache key is derived from the rendered prompt up to a marked breakpoint. Any change anywhere in the prefix invalidates everything after it.

Render order is fixed: tool definitions first, then the system prompt, then messages. So a change to your tool list invalidates literally everything. A change to the system prompt invalidates system and messages. A change to message content invalidates only messages.

The economics

OperationCost vs normal input
Cache readabout 0.1x
Cache write, 5 minute lifetime1.25x
Cache write, 1 hour lifetime2x

Break-even with the short lifetime is two requests (1.25 + 0.1 = 1.35, versus 2.0 uncached). With the hour lifetime you need three. After that it is close to a ninety percent discount on everything cached, which on a large stable system prompt is the difference between a viable product and an unviable one.

The silent invalidators

These are the ones that bite, because nothing errors. You just quietly pay full price forever.

PatternWhy it breaks caching
datetime.now() in the system promptThe prefix differs on every single request
A request ID or UUID near the topSame. Every request is unique.
json.dumps(d) without sorting keysNon-deterministic serialization, so the bytes differ
User ID interpolated into the system promptPer-user prefix, no sharing across users
Conditional system sectionsEvery flag combination is a separate prefix
A tool list that varies by user or modeTools render first, so nothing caches at all

How to actually verify

The response reports what happened. Check it, do not assume:

usage.cache_creation_input_tokens   written this request (you paid the premium)
usage.cache_read_input_tokens      served from cache (you paid ~10%)
usage.input_tokens                 full price, not cached

If cache reads are zero across repeated requests with what you believe is an identical prefix, you have an invalidator. Diff the actual rendered bytes of two requests. It is always something small and always something you did not think of as part of the prompt.

A second gotcha: input_tokens is only the uncached remainder. Total prompt size is the sum of all three fields. An agent that ran for hours and reports 4,000 input tokens did not use 4,000 tokens; the rest came from cache.

Design rules that follow

  • Freeze the system prompt. Never interpolate the date, the user, or the mode into it. Inject those later in the message array where they invalidate nothing before them.
  • Sort your tools deterministically and do not change the set mid-conversation.
  • Do not switch models mid-conversation. Caches are per-model. If a sub-task wants a cheaper model, spawn a subagent for it and keep the main loop on one model.
  • Place the breakpoint at the end of the shared part, not at the end of the whole prompt. If you cache through the varying question, every request writes a new entry and nothing is ever read.
  • Fan-out needs a warm-up. A cache entry is only readable once the first response starts streaming. Fifty parallel identical-prefix requests all pay full price. Send one, wait for the first token, then send the other forty-nine.

Other cost levers, in order of size

  1. Caching. Up to 90 percent on the repeated portion. Nothing else comes close.
  2. Batch processing. Flat 50 percent off for anything that can tolerate up to 24 hours of latency. Absurdly underused.
  3. Effort tuning. Dropping from the top setting to medium on routine work is often invisible in quality and very visible on the bill.
  4. Model routing. Real, but smaller than people assume, and it comes with a cache penalty when you switch mid-session.
  5. Shorter prompts. Last, and mostly a distraction. Deleting context to save tokens usually costs more in retries than it saves.

If you have no per-surface token accounting, add that before optimizing anything. Every issue in this section is invisible without it.

Section 5Claude Code as a system

In one line

Four layers: instructions that always load, skills that load on demand, connectors that add capability, and subagents that add parallelism.

Instruction files

A CLAUDE.md in a project root loads into context automatically, every session, every turn. That is its power and its cost. It is prime real estate at the high-attention start of the buffer, and everything in it is paid for on every request.

Belongs there

Architecture and how the pieces relate. Where the canonical source lives. Conventions that are not guessable. Commands to run and verify. Hard style rules. Things that will bite someone who does not know them.

Does not belong

General programming knowledge. Restatements of trained defaults ("write clean code"). One session's stumble encoded as a permanent rule. Anything the repository already makes obvious. Incident archaeology and PR numbers.

The test for any line: could the model already know this? Keep what only you know. That is the whole rule, and it is why "be helpful and accurate" is pure waste while "the canonical source is this file, copy it to the others" is worth its weight.

The recency trap deserves its own warning. After a bad session it is tempting to write a rule preventing exactly that stumble. Before you do, ask whether the rule would have helped the last ten sessions or only the one that just annoyed you. Instruction files rot into a minefield of one-off patches otherwise.

Skills

A skill is a folder with instructions that load only when relevant. Its short description sits in context permanently; the full body loads when the task matches. That is progressive disclosure, and it is the mechanism that lets you have fifty specialized workflows without paying for fifty specialized workflows on every request.

When to create one, in practical terms: the third time you do a task by hand. Once is a task. Twice is a coincidence. Three times is a process, and processes should be written down where the model can find them.

Skill design notes worth internalizing:

  • Match specificity to fragility. Exact scripts for the narrow bridges where only one sequence is safe. Prose heuristics for the open fields where judgment beats a checklist. Getting this backwards is the most common skill failure: rigid scripts for judgment calls, vague hand-waving for the destructive command.
  • Size is a tax on every trigger. If a skill file cannot be read in one sitting, it is too long.
  • The description is the trigger. It is the only part always in context and the only thing deciding whether the skill fires. Write it as categories of intent, not as a growing list of example phrasings.
  • Encode architecture, not trivia. Hardcoded paths, flags, and version numbers rot as code ships. Data models and workflows do not.

Connectors

MCP servers give the model tools it did not otherwise have: a database, a broker, a calendar, an issue tracker. Two facts that catch people out.

First, connectors are scoped. Tools available in one project are not available in another. If you built tooling for one workspace, it does not follow you into a different directory, and that is deliberate.

Second, credentials never belong in prompts. They belong in the connector's own configuration or a secret store. A key pasted into a message is persisted in the conversation history and replayed forever.

Subagents

A subagent is a fresh context window doing a scoped piece of work and reporting back. The appeal is obvious: parallelism, and isolation of a messy exploration from your main thread.

The cost is less obvious and larger than people expect. Each subagent has to re-establish context from nothing, re-explore, form conclusions, and write a report. Then the parent reads the report. You pay for the setup, the work, the report, and the reading, and you lose all the nuance that did not fit in the report.

Worth it

Genuinely independent tracks. Wide multi-file investigation where each branch is self-contained. Work you want to fan out and are happy to receive as a summary.

Not worth it

Anything you could finish in a handful of tool calls yourself. Sequential work with dependencies. Verification and double-checking (that belongs in the main loop). Splitting one modest job into pieces.

The current frontier models lean toward delegation, which is a reversal from the previous generation that had to be nudged into it. If you carried forward a "delegate more aggressively" instruction from a year ago, delete it, and consider capping spawn counts explicitly instead.

Plan mode and permissions

Plan mode separates "figure out what to do" from "do it." It is worth reaching for whenever the cost of a wrong approach exceeds the cost of a round trip: unfamiliar codebases, anything touching data, anything where you would rather review a plan than a diff.

Permission modes are a real safety boundary and a real productivity dial, and they trade against each other honestly. The useful habit is to match the mode to the blast radius: loose in a scratch directory or a throwaway branch, tight anywhere a mistake is expensive to undo.

Section 6Tools and agents

In one line

Most things people build as agents should have been a workflow, and most agent failures are tool-design failures.

The tiers

TierShapeRight for
Single callOne request, one responseClassify, summarize, extract, answer
WorkflowSeveral calls, your code controls the orderMulti-step pipelines with a known shape
AgentThe model decides what to do next, in a loopOpen-ended tasks you cannot fully specify up front

Start at the top and only move down when forced. The strong default is that a workflow beats an agent whenever the steps are knowable in advance, because deterministic control flow is debuggable and a model-driven loop is not.

The four-question test

Before building an agent, all four must pass:

  1. Complexity. Is the task genuinely multi-step and hard to specify up front? "Turn this design doc into a pull request" qualifies. "Extract the title from this PDF" does not.
  2. Value. Does the outcome justify the cost and the latency? Agents are expensive and slow relative to a single call.
  3. Viability. Is the model actually good at this class of task? Not "could it in principle," but "does it, reliably, today."
  4. Cost of error. Can mistakes be caught and undone? Tests, review, rollback, an audit trail. If a wrong action is silent and permanent, do not build an agent.

A "no" on any one of these means stay at a simpler tier. The fourth one is the one people wave past, and it is the one that produces the horror stories.

Tool design is the actual work

The quality of an agent is mostly determined by its tool surface, not its prompt. A few principles that hold up:

Descriptions are the highest-leverage text you will write. Not the system prompt: the tool descriptions. Under-description is the most common failure by a wide margin. Three or four sentences minimum, covering what it does, when to use it, when not to, what each parameter means, and what it does not return.

Be prescriptive about triggering, not just descriptive about function. "Returns current stock quotes" is weaker than "Call this whenever the answer depends on a current price. Do not use it for historical analysis." Current models reach for tools conservatively, and the trigger condition in the description measurably raises the should-call rate.

Start with a broad tool, promote to specific ones. A shell gives the model maximum leverage but gives your harness an opaque string. Promote an action to its own tool when you need to gate it (destructive or irreversible), render it (custom UI), audit it, or parallelize it safely. A send_email tool is easy to put behind a confirmation. A shell command that happens to contain a curl to a mail API is not.

Fewer, clearly bounded tools beat many overlapping ones. If two tools have descriptions that a careful reader would confuse, the model will confuse them too. Say the boundary explicitly in both.

Return high-signal results. A tool that dumps 40,000 tokens of JSON when the model needed three fields is burning context on every call. Filter server side.

Verification is the difference between a demo and a system

The thing that separates agents that work from agents that impress once is a feedback loop the agent can actually run. Tests. A type checker. A linter. A schema validator. A second model with a rubric. Anything that turns "I think this is right" into a signal.

Without it the agent has no way to distinguish plausible from correct, which is section 1's problem showing up at the system level.

How agents fail, specifically

  • Context exhaustion. Fills the window with tool output, degrades, loses the plot. Section 3 is the mitigation.
  • Loops. Tries the same failing approach repeatedly with cosmetic variation. Almost always because the error message it gets back is uninformative. Fix the tool's error output, not the prompt.
  • Silent partial completion. Reports success having done sixty percent. This is why "report outcomes faithfully, and if a step was skipped say so" earns its place in a system prompt, and why you need external verification anyway.
  • Scope creep. Asked to fix a bug, refactors the module. Bounded by an explicit scope instruction (section 2).
  • Confident wrong premises. Misreads something early, builds twenty steps on it. See poisoning, section 3.

Notice how many of these are fixed by better tool output rather than better prompting. That is the general shape of agent debugging.

Section 7Picking a model

In one line

Pick the strong default, then tune effort. Effort moves cost and latency more than model choice does.

The shape of the lineup

Every provider now offers roughly the same three tiers, and the reasoning transfers:

  • A frontier tier for the hardest reasoning and longest-horizon autonomous work. Most expensive, slowest, and genuinely better on problems the tier below cannot finish.
  • A workhorse tier that handles the large majority of real work, including most coding and agentic tasks. This is where you should default.
  • A fast tier for high-volume, latency-sensitive, mechanically simple work: classification, routing, extraction, formatting.

The mistake people make is treating the frontier tier as "the good one" and everything else as a compromise. In practice the workhorse tier at high effort beats the frontier tier at low effort on most tasks, and costs less.

Effort, revisited

Worth repeating because it is the lever people leave untouched. Effort defaults to high. That is a reasonable default and it is usually not the right setting for your specific route.

A practical procedure: take a representative sample of your actual workload, run it at low, medium, high, and xhigh, and look at quality against cost and latency. The relationship is frequently not monotonic. Routine work often shows no quality difference between medium and max while costing a fraction. Hard agentic work often shows the opposite, where higher effort means fewer wasted rounds and lower total cost.

Effort settings carried over from a previous model generation are almost never right. Re-sweep on every upgrade.

A trap

Effort is not a verbosity control. If responses are too long, lowering effort may reduce reasoning without shortening the visible answer at all. Verbosity is a prompting problem: ask for concision explicitly, and it works.

When routing between models is worth it

Genuinely worth it when: the volume is high, the tasks are cleanly separable by difficulty, and each route has its own stable prompt so caching is not disrupted.

Not worth it when: you would be switching models mid-conversation (this destroys the cache), the classification of which task is hard is itself hard, or the volume is low enough that the engineering cost exceeds the savings.

The clean pattern is a subagent on a cheaper model for a scoped sub-task, with the main loop staying on one model throughout.

Section 8Knowing whether you improved anything

In one line

Twenty saved test cases beat any amount of intuition, and asking the model whether your prompt is good is not a measurement.

Why intuition fails here

These systems are non-deterministic and you are prompting them while holding a hypothesis. That combination is close to a laboratory for confirmation bias. You change a line, the next output looks better, you conclude the line helped. It may have been variance. It may have been a different input. It may have been that you read the output more charitably because you expected improvement.

The minimum viable eval

This is genuinely small and almost nobody does it:

  1. Collect 20 real inputs. Not synthetic ones. Real ones from your actual use, deliberately including the hard and weird cases, because those are the ones a prompt change breaks.
  2. Write down what a good output looks like for each. Not necessarily a full gold answer. Often a checklist of three things it must get right is more useful, and much faster to write.
  3. Run all 20 before your change. Save the outputs.
  4. Make exactly one change.
  5. Run all 20 again and diff.

An afternoon of setup, and after that every prompt change becomes an experiment rather than a vibe. The step people skip is the fourth one: changing three things at once and then being unable to attribute the result is the most common way an eval set gets abandoned.

The self-report trap

Asking a model "is this prompt good?" or "do you need this instruction?" produces fluent, confident, plausible commentary that is unrelated to what the model will actually do. It does not have introspective access to its own behavior. It is predicting what an answer to that question looks like.

The same applies to "did you check everything?" The answer is yes. The answer is always yes. Verify externally or do not verify.

Removal is a hypothesis

When you delete a line from a prompt, that is a hypothesis that the line was not doing anything. Test it like one: run the eval, and if quality drops, put back a minimal version rather than restoring the original wall of text.

This matters because prompts only ever grow otherwise. Every incident adds a line; nothing removes one. Six months later you have a document nobody understands, where half the lines are patches for a model that no longer exists, and where the accumulated caution is measurably degrading output.

Section 9Failure modes, catalogued

A diagnostic table. Symptom on the left, likely cause and fix on the right.

Under-triggers a toolThe tool description says what it does but not when to call it. Add the trigger condition to the description itself.

Section 10Drills

Nothing here needs a connection. A notebook is enough, and the point is to have the work already done when you are back online.

Drill 1 · Audit an instruction file

Take a CLAUDE.md or system prompt you rely on and go through it line by line with one question: could the model already know this? Mark every line KEEP, CUT, or UNSURE. Then count the CUTs. In most real prompts it is between a third and a half. Do not act on it yet, just make the list.

Drill 2 · Date the fossils

In the same document, find every line containing MUST, NEVER, CRITICAL, ALWAYS, or an all-caps word. For each, write down what failure it was preventing and which model it was written for. Any line where you cannot answer either question is a removal candidate. Any line naming a model you no longer use is a removal candidate with high confidence.

Drill 3 · Build the eval set

Write out 20 real inputs from something you actually use. Next to each, three bullet points describing what a correct output must contain. This is the highest-value hour in this entire guide, and it is fully doable offline.

Drill 4 · Rewrite the context header

Pick a task you do repeatedly. Write the context block you should be leading with every time: who it is for, what it plugs into, what the constraints are, what good looks like. Aim for a paragraph you can paste. Most people discover they have been re-explaining this from scratch, badly, every time.

Drill 5 · Find the cache invalidator

For each place you build a prompt programmatically, write out in order what goes into the prefix. Circle anything that could vary between two requests you would expect to share a cache. Dates and IDs are the usual suspects; unsorted dictionary serialization is the sneaky one.

Drill 6 · The third-time inventory

List every task you have done by hand three or more times in the last month. Each one is a skill you have not written yet. Sketch the description line for each, since that is the part that decides whether it ever fires.

Drill 7 · Agent triage

Take something you have considered automating and run the four-question test honestly: complexity, value, viability, cost of error. Then write down what the verification loop would be. If you cannot name one, you have your answer, and it is a workflow rather than an agent.

Drill 8 · Write the tool description

Pick a tool you already expose and rewrite its description from scratch: what it does, when to call it, when explicitly not to, what each parameter means, what it does not return. Compare to what is there now. This is usually where the biggest uncaptured gain is hiding.

Things that changed and will trip up old code

  • Fixed thinking budgets are gone. budget_tokens errors on current models. Use adaptive thinking plus effort.
  • Sampling parameters are gone. temperature, top_p, and top_k are rejected on current frontier models. Steer with prompting instead. For variety in creative or design work, ask the model to propose several distinct directions and pick one.
  • Assistant prefills are gone. The trick of starting the assistant turn with {" to force JSON now errors. Use structured outputs instead, and delete the whole apparatus around the prefill: stop sequences, regex extraction, parse-retry loops.
  • Reasoning is hidden by default. If you were rendering thinking text to users, it will now be empty unless you opt into summaries.
  • Thinking counts against the output cap. A request that was comfortably sized before can truncate once thinking is on.

The compressed version of this whole guide

  1. Context is the lever. Phrasing is not.
  2. The model is stateless. Everything is resent, every turn.
  3. Middle-of-context material gets less attention. Placement beats emphasis.
  4. Say it once, plainly. Emphasis written for old models now overshoots.
  5. Describe success, not a list of failures.
  6. Examples outrank instructions. Vary them.
  7. Give the reason behind the request.
  8. State the boundary, or it will exceed the scope.
  9. Delete "double-check your work". It over-verifies now.
  10. Retrieval beats recall. Give it the document.
  11. Caching is a prefix match. One timestamp costs you everything.
  12. Batch anything that tolerates latency. Fifty percent off.
  13. Sweep effort. The default is not your answer.
  14. Third time by hand means write a skill.
  15. Tool descriptions matter more than the system prompt.
  16. An agent without a verification loop is a demo.
  17. Twenty saved test cases beat any amount of intuition.
  18. Prompts are per-model artifacts. Re-read and delete on every upgrade.
